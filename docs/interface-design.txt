HEADROOM INTERFACE STUDY — NOVEMBER 11, 2026

Branch: design/interface-refresh (local experiment; main is unchanged).

Compared three coded layout prototypes using the same three example accounts,
long email, capacity totals, and forecast, at a 1200 x 780 viewport. Evaluated
headlessly through DOM bounds, without controlling or capturing the desktop.

Gallery: expanded cards, large capacity and forecast panels. Last account
bottom at 916 px. Familiar, but repeats labels and reserves too much space
for empty resets and secondary actions.

Sidebar: persistent navigation and vertically stacked insights. Last account
bottom at 1216 px. Gives future sections room, but consumes useful account
width and pushes essential balances below the fold.

Focus: capacity and runway side by side, aligned account rows, separate Activity
view. Last account bottom at 832 px in the rough prototype, with room to tighten
spacing in implementation. No email clipping or horizontal page overflow.

Selected direction: Focus. Keep capacity and runway immediately visible, put
account identity, allowance, reset time, and banked resets into predictable
columns, and move destructive actions into account menus. Keep information
about calculations available in disclosures. Activity gets dedicated space
for scenario controls and graphs without crowding everyday monitoring.

Visual direction: six complete dark palettes, with Ember as the default.
Ember uses warm charcoal, copper, and sand; Orchard uses olive and citrus;
Lagoon pairs deep teal and sea glass with coral; Rosewood pairs wine and rose
with brass. Classic restores the original slate/periwinkle/mint palette, while
Graphite uses neutral black/gray surfaces and silver accents and chart lines.
Semantic color roles cover surfaces, text, controls, charts, and
loading states. Tabular numbers, one spacing scale, visible keyboard focus,
reduced-motion support, and compact loading/empty/error states are shared.
Account colors stay consistent across filtering within each theme.

The custom title bar, controls, and frame are drawn by the app. Windows keeps
native move/resize/snap behavior, but must not draw its title bar or border.
No additional frontend dependencies or network fonts are introduced.

Implemented layout: at 1200 x 780, the third account ends at 681 px. Both
capacity and runway summaries and all three account rows fit without scrolling.
Validated at 520, 680, 800, 1024, 1200, 1440, and 2560 px: consistent section edges,
long emails on one line, no horizontal overflow, SVG labels inside their plots,
and captions separated from axis text. Smaller windows use stacked account
sections; the 520 px case also covers a small window under display scaling.
Larger account sets remain searchable and scroll vertically.

The Overview always summarizes all accounts at recent pace, including verified
banked resets. Activity account filters and scenario controls remain independent.
Account menus support Escape and restore focus; refresh remains named for screen
readers when its text is hidden in small windows. History failure has an explicit
retry state instead of an endless loading animation.

The app name, navigation, actions, and window controls now share one seamless
header surface. Narrow windows use two rows on that same surface. The header
never scrolls; the main content owns page scrolling. The theme chooser fits
inside short windows and returns keyboard focus on Escape. Preferences use
the portable settings file, not browser storage tied to a random loopback port.
Initial HTML includes the selected palette to avoid a flash of the wrong theme.
Theme and startup preference updates preserve each other under a shared lock.

The headless audit covers all seven widths, all six themes, 4.5:1 normal-text
contrast, 3:1 chart contrast, bounded menus, overlapping controls, unwanted
header scrollbars, save-failure recovery, and a reload in the selected theme.
An isolated EXE test covers API validation/authentication, persistence across
restart, initial HTML, and preservation of Codex/startup preferences.

Each palette includes matching SVG, ten-size ICO, and 512px PNG artwork, generated
from the CSS accents by tools/Build-Icon.ps1. Classic preserves the original art.
The page's loading icon and favicon are selected before first paint. Only the
interface icon follows the selected theme. The EXE, native window/taskbar, tray,
and launch shortcuts always use Graphite. AppIcon.WindowIcon has no theme input;
theme saves persist the interface preference without calling any native icon API.
The native theme-update method and tray icon replacement method were removed.
Windows icon handles are loaded once, retained for the window lifetime (including
Explorer restart recovery for the tray), and released on shutdown. Linux uses the
fixed Graphite PNG through Photino's native window icon API.
The EXE's ten published RT_ICON resources are compared byte-for-byte with the
Graphite ICO during the single-EXE check. The headless self-test decodes all sixty
legacy/native icon frames and checks migration of scratch shortcuts to Graphite.
Appearance checks cover all six interface palettes, persistence and initial paint.

Windows taskbar icons: documented behavior and implementation

The window icon and grouped taskbar icon are different. Microsoft explains that
the group icon can come from Start menu or desktop shortcuts. WM_SETICON alone
does not guarantee an update to a pinned or combined taskbar button.
https://devblogs.microsoft.com/oldnewthing/20150812-00/?p=91831/
https://github.com/microsoft/WindowsAppSDK/issues/2730

Microsoft's AppUserModelID guidance says to keep the same identity across the
process and its launch shortcuts. When a shortcut exists, use its properties
instead of window relaunch properties. The adapter updates existing per-user
desktop, Start menu and taskbar links only when their target matches this EXE.
It preserves arguments, working directory and descriptions, and never pins an
application or changes its identity per theme. Older redundant relaunch values
are removed. If no shortcut exists, the window supplies relaunch metadata using
the documented ICO resource format (path.ico,0), and sets its stable ID last.
https://learn.microsoft.com/en-us/windows/win32/shell/appids
https://learn.microsoft.com/en-us/windows/win32/properties/props-system-appusermodel-relaunchiconresource
https://learn.microsoft.com/en-us/windows/win32/properties/props-system-appusermodel-id

At startup, launch links are migrated to data/icons/headroom-graphite.ico.
Before changing a shortcut, the adapter captures its old Shell icon location,
index and flags through IExtractIcon::GetIconLocation, and its system image-list
index through SHGetFileInfo(SHGFI_SYSICONINDEX). SHUpdateImage then notifies the
Shell of the changed image using those OLD parameters, as Microsoft specifies.
Targeted SHCNE_UPDATEITEM notifications announce changed shortcut files. The
Graphite file is immutable and independent of the saved interface theme.
https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shupdateimagew
https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-iextracticonw-geticonlocation
https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ishelllinkw-seticonlocation

The previous visibility-cycle and DeleteTab/AddTab workarounds were removed.
Theme updates never hide/show, activate, reposition or recreate the window/button.
They must not disturb Windows Snap. No Explorer restart or global cache reset.

The user confirmed that live changes worked with Never Combine and failed with
Always Combine while unpinned. A fixed Graphite identity on all OS surfaces is the
chosen workaround; theme changes no longer attempt a taskbar repaint.

Validation uses scratch links and a message-only HWND. It cycles legacy/Graphite icons,
checks the pixels returned by the Shell (rendered into an in-memory bitmap, not
a screen capture), preserves unrelated targets and launch details, verifies
shortcut/no-shortcut metadata, and leaves hidden windows hidden. This validates
Shell extraction/cache behavior; it does NOT establish that Explorer's visible
grouped taskbar button has repainted. Microsoft's documentation does not promise
synchronous repaint of every taskbar configuration. User verification of pinned,
unpinned, snapped and maximized cases remains necessary. Do not claim otherwise
based on metadata or API success alone.

WM_NCCALCSIZE continues to provide the full client area. On Windows 11, DWM
non-client rendering is enabled for real outer-window clipping and shadow;
DWMWCP_ROUND requests rounded corners and DWMWA_COLOR_NONE hides its border.
No competing CSS outline or corner is drawn. Older Windows falls back to a
square custom frame with non-client rendering disabled. Maximized and snapped
windows follow the system's square corners. The native move/resize logic stays.
Native interactions still require manual verification; no desktop control or
screen capture was used during this redesign.
